## 1. Outcome

After a recording passes the quality rules, the server runs a real model on the laptop (no internet) and stores
**murmur / no murmur / too poor to judge** with a confidence, the model name and version. The doctor sees it on the
result page that already exists (task 5). For the commission and the ISR we can say **how accurate it is, measured by
us, on patients the model never saw**.

Signal that it worked: an evaluation report (`docs/specs/ai-results.md`) with sensitivity, specificity and accuracy on
held-out CirCor patients, and a live demo where the AI card shows a real answer within ~10 s of the upload.

Facts checked on this laptop / online:
- **CardioPHON input**: 4 kHz, log-mel 64 bands (60–2000 Hz), windows of 0.95 s, embedding 3072 numbers per window;
  fixed normalisation numbers in the script. Demographics (age group, sex, pregnancy, BMI group) are optional
  ("multi" mode); "uni" mode is audio only.
- **PyTorch for Python 3.14 exists**: `torch 2.15.0+cpu` resolves for our Python (dry run, nothing installed).
- **CirCor full dataset**: 3 163 recordings of 942 patients, zip **471 MB** (559 MB unpacked), open access
  ([PhysioNet](https://physionet.org/content/circor-heart-sound/1.0.3/)). We have only 8 sample files now.

**What this changes in PLAN §5:**
1. "Run CardioPHON as is" is impossible: there is no trained murmur classifier to run. We must train the last small
   layer ourselves (minutes on the laptop CPU, from the shipped encoder). That is the "oxirgi qatlamni o'qitish kerak
   bo'lishi mumkin" risk in PLAN — it is now certain.
2. The CardioPHON quality model is not shipped. Our existing rules (`services/quality.py`) stay the quality gate; the
   model's own "Unknown" answer becomes "too poor to judge".
3. AST can be compared, but its CirCor numbers cannot be trusted (probable train/test overlap). This must be said
   openly in the ISR.

## 3. Approaches

```
Option A — AST as is (download, run).
  Fits: labels already match our vocabulary; least code.
  Costs: 345 MB model + transformers; 16 kHz input; we can never say how accurate it really is on CirCor.
Option B — CardioPHON encoder + our own small murmur head, trained on CirCor with a patient-level split (80 % train,
  20 % test, a patient is never in both).
  Fits: PLAN's cited source [1]; honest numbers measured by us; small and fast at run time; 4 kHz like our device.
  Costs: a training script and an inference adapter (~250 lines); 471 MB data download; no-licence question.
Option C — B for production, plus one evaluation script that runs A and B on the same held-out patients.
  Fits: PLAN asks for a two-model comparison for the ISR.  Costs: A's numbers come with a caveat (possible overlap).
Recommendation: C. The commission's first question will be "how accurate is it?" — only B answers it honestly; A
costs one extra function in the evaluation script and gives the comparison PLAN promised.
```

Inside B, **audio only ("uni" mode)**, not demographics: CirCor patients are children (oldest group "young adult");
our demo patients are adults, so age/BMI inputs would be outside what the model learned. Audio-only is simpler and
more honest. Demographics can be tried later in the evaluation script.

**Per-recording labels** (we record one point per exam, CirCor labels are per patient): Present if the recording's
point is in the patient's murmur locations; Absent if the patient has no murmur; Unknown if the patient is Unknown;
recordings of Present patients at points without an audible murmur are left out (ambiguous).

## 5. Edge cases

1. Model files missing / `ai` group not installed → log once, fall back to dummy; admin sees model "dummy".
2. Smart App Control blocks PyTorch's native files (like it blocked pytest.exe and oxlint) → found in step 1 (spike);
   fallback: export the model to ONNX and run it with onnxruntime (Microsoft-signed), at extra work.
3. Recording not 4 kHz (ESP32 may send 8/16 kHz) → resample to 4 kHz before the model.
4. Recording shorter than one window / silent parts → already rejected by quality rules (< 10 s); windows averaged.
5. Model says "Unknown" → stored as quality `bad` → "Recording too poor to judge" + Record again.
6. First analysis after start loads the model (a few seconds) → acceptable; later ones reuse it.
7. Two uploads at once → BackgroundTasks run in threads; inference under a lock, one at a time.
8. Model crashes on a file → existing path: exam `failed`, "analysis error", recording kept.
9. Children vs adults, clinical stethoscope vs cheap microphone → accuracy will drop; stated in the UI disclaimer
   (already there) and in the ISR limits.
10. Retraining changes results → every result stores model name + version (e.g. `cardiophon-murmur 1.0.0`); the
    version is bumped on every retrain.
11. Class imbalance (CirCor: far more Absent than Present) → class weights in training; report sensitivity, not only
    accuracy.

## 6. Out of scope (now)

CardioPHON quality model (needs 4 more datasets), demographics ("multi" mode), fine-tuning the encoder, GPU, S1/S2
segmentation, outcome Normal/Abnormal, ONNX (only if step 1 fails).

## 7. Steps and verification (each step ends with a check)

1. **Spike** — install the `ai` group; `uv run python -c "import torch; print(torch.__version__, torch.randn(2).sum())"`
   prints a number (not blocked). Load the CardioPHON encoder and embed one sample WAV → 3072 numbers.
2. **Data** — download CirCor (471 MB) to `samples/circor/`; check 3 163 WAV files and the patient table.
3. **Train** — `uv run python ../scripts/ai/train_head.py` → patient-level split saved to a file (reproducible, seed),
   head saved to `models/`, training report printed.
4. **Evaluate** — `uv run python ../scripts/ai/evaluate.py` → confusion matrix, sensitivity, specificity, accuracy
   for B (and A with its caveat) on the held-out patients → written to `docs/specs/ai-results.md`.
5. **Plug in** — `CardiophonAnalyzer` + config switch + fallback. Tests (no model files needed): label/Unknown/score
   mapping, resampling, missing files → dummy, crash → failed. `uv run python -m pytest` all green, ruff clean.
6. **Demo run** — fake device + browser: the AI card shows "Murmur detected / No murmur detected" with confidence and
   `cardiophon-murmur 1.0.0`; screenshot.

## 8. Self-critique

- Weakest assumption: the shipped encoder + a small head reaches useful accuracy on single 20 s recordings. If not,
  the evaluation says so with numbers, and that is still a valid ISR result; we would not hide it.
- 80/20 alternative: run AST as is (Option A) in an afternoon. Rejected as the main model because it cannot be
  measured honestly — a demo of a number we cannot defend is worse than a smaller honest one.
- What a generic assistant would do: "pip install transformers, run the HF model". The research above (no trained
  CardioPHON head, no licence, AST overlap) is why this plan is different.
